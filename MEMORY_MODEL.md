# Модель памяти агента

Агент работает с **пятью независимыми слоями**, каждый из которых хранится в
каталоге `memory/<agent>/`. Отдельно от диалога хранятся **инварианты** —
жёсткие ограничения высшего приоритета (см. раздел «Инварианты»).

## Инварианты

- **Назначение:** жёсткие ограничения, которые агент не имеет права нарушать.
  Примеры: выбранная архитектура, принятые технические решения, ограничения по
  стеку, бизнес-правила. Это отдельный слой, **более приоритетный, чем профиль**.
- **Хранение:** отдельный файл на агента — `memory/<agent>/invariants.json`.
- **Привязка к агенту** (не к задаче, не глобально): у каждого агента — свой
  набор инвариантов.
- **Действуют всегда:** и при активной задаче, и без неё, и при задаче на паузе,
  и при завершённой задаче.
- **Включаемость:** слой включается/выключается командой
  `/memory usage invariant on|off` (по умолчанию — on). При выключении блок
  инвариантов не подмешивается в промт и пост-проверка не выполняется, но файл
  `invariants.json` не удаляется.

### Схема файла `invariants.json`

```json
{
  "invariants": [
    {
      "id": "uuid",
      "category": "architecture|tech|stack|business|other",
      "text": "Не использовать Flask — только FastAPI.",
      "ts": "ISO8601"
    }
  ]
}
```

Поля: `id` (UUID, не переиспользуется после удаления), `category`, `text`, `ts`.

### Механика соблюдения

Используется гибридный подход:

1. **Через промт.** Блок инвариантов подмешивается в промт (выше профиля).
   System prompt инструктирует модель: «Никогда не предлагай решения, нарушающие
   инварианты. Если запрос пользователя требует нарушения инварианта — откажи и
   объясни, какой инвариант нарушается».
2. **Пост-проверка (LLM-валидатор, опционально).** После ответа основной модели
   запускается отдельный вызов LLM с промтом вида:

   ```
   Вот список инвариантов: <...>. Вот ответ ассистента: <...>.
   Нарушает ли этот ответ хотя бы один инвариант? Ответь строго: "OK" или "VIOLATION: <id инварианта>".
   ```

   - `OK` — ответ отдаётся пользователю.
   - `VIOLATION` — пользователю показывается только текст отказа
     «Предложенное решение нарушает инвариант X.». Исходный ответ агента не
     показывается. Уточнение, какой именно инвариант, — по формулировке
     валидатора (ID).

Пост-проверка включается/выключается командой `/invariant check on|off`
(по умолчанию — off, чтобы не тратить токены). При `/invariant check on`
пост-проверка выполняется после каждого ответа агента.

### Управление инвариантами

- `/invariant list` — список инвариантов агента (ID, категория, текст);
- `/invariant add <category> <текст>` — добавить инвариант;
- `/invariant del <id>` — удалить инвариант по ID;
- `/invariant edit <id> <текст>` — изменить текст инварианта;
- `/invariant clear` — очистить все инварианты;
- `/invariant check on|off` — включить/выключить пост-проверку.

## Слои

### 1. Профиль (profile)
- **Назначение:** отдельный слой памяти, более приоритетный, чем long-term.
  Описывает пользователя: предпочтения по стилю, формату, ограничениям.
- **Хранение:** отдельный файл на профиль — `memory/<agent>/profiles/<name>.json`.
- **Активный профиль:** имя активного профиля хранится одной строкой в файле
  `memory/<agent>/active_profile.txt`. Если файл отсутствует или пуст — активного
  профиля нет.
- **Обязательные поля:** `style`, `format`, `constraints` — ключи присутствуют
  всегда, но могут быть пустыми строками.
- **Произвольное поле:** `notes` — список строк; заметки добавляются и удаляются
  отдельными командами.
- **Изоляция:** у каждого агента — свой набор профилей. Переключение агента не
  влияет на профили других агентов.

### 2. Краткосрочная (short-term)
- **Назначение:** лог диалога в рамках активной задачи.
- **Файл:** `memory/<agent>/short_term.json`.
- **Персистентность:** между запусками приложения, пока слой не очищён командой
  `/memory clear short` или автоматически при `/task new` / `/task switch`.
- **Правило сохранения:** если активной задачи нет — краткосрочная память
  **не сохраняется** (работает только в памяти текущей сессии).

### 3. Рабочая (working)
- **Назначение:** данные текущей задачи.
- **Файл:** `memory/<agent>/working_<task_name>.json` — один файл на задачу.
- **Доступность:** завершённая задача сохраняется в файл, но становится
  недоступной, пока её не активируют заново (`/task switch <name>`).
- **Правило сохранения:** если активной задачи нет — рабочая память не
  используется и не сохраняется.

### 4. Долговременная (long-term)
- **Назначение:** решения и знания.
- **Файл:** `memory/<agent>/long_term.json`.
- **Формат:** единый список записей с полем `type`: `decision | knowledge`.
- **Доступность:** всегда доступна для агента.

## Политика попадания в память

**Только вручную** — авто-классификация не используется. Пользователь сам
указывает слой при сохранении:

- **Команды** (всегда доступны): `/memory add ...` отдельно от диалога. Любое
  сообщение пользователя автоматически попадает в short-term как часть диалога.
- **Диалог подтверждения** (опционально, `/prompt_save on`): после каждого
  ответа агент спрашивает «Сохранить куда? [short/working/long/none]».

Сохранять в память можно и сообщения пользователя, и ответы агента.

## Приоритет и порядок в промте

Промт формируется в порядке:

```
system prompt агента
→ invariants (новый, высший приоритет)
→ profile
→ long-term
→ working
→ блок состояния задачи (FSM, если есть этапы и задача не на паузе и не завершена)
→ short-term (текущий диалог)
→ текущий запрос пользователя
```

В system prompt модель явно инструктируется: «При конфликте информации следуй
более приоритетному слою: invariants > profile > long-term > working >
short-term», а также «Никогда не предлагай решения, нарушающие инварианты.
Если запрос пользователя требует нарушения инварианта — откажи и объясни, какой
инвариант нарушается».

## Схема файлов

### `active_profile.txt`

```
имя_активного_профиля
```

Одна строка — имя активного профиля. Если файл отсутствует или пуст — активного
профиля нет, и слой profile в промт не подмешивается.

### `profiles/<name>.json`

```json
{
  "name": "work",
  "style": "строгий, деловой",
  "format": "markdown, без воды",
  "constraints": "не использовать эмодзи; отвечать кратко",
  "notes": [
    "предпочитает примеры кода на Python",
    "не любит извинения"
  ],
  "created_at": "ISO8601",
  "updated_at": "ISO8601"
}
```

### `short_term.json`

```json
{
  "task": "название активной задачи",
  "messages": [
    {"id": "uuid", "role": "user|assistant", "content": "...", "ts": "ISO8601"}
  ]
}
```

### `working_<task_name>.json`

```json
{
  "task": "название",
  "created_at": "ISO8601",
  "records": [
    {"id": "uuid", "content": "...", "ts": "ISO8601"}
  ],
  "fsm": {
    "stages": [
      {
        "name": "planning",
        "description": "...",
        "condition": "...",
        "expected_action": "...",
        "status": "completed",
        "order": 0
      },
      {
        "name": "execution",
        "description": "...",
        "condition": "...",
        "expected_action": "...",
        "status": "active",
        "order": 1
      }
    ],
    "current_stage": "execution",
    "paused": false,
    "completed": false
  }
}
```

Поле `fsm` может отсутствовать или быть `null` — тогда задача работает как обычный
диалог с рабочей памятью (без этапов).

### `long_term.json`

```json
{
  "records": [
    {"id": "uuid", "type": "decision|knowledge", "content": "...", "ts": "ISO8601"}
  ]
}
```

Идентификаторы — UUID; не переиспользуются после удаления.

## Правила очистки и переключения задач

- `/task new <name>` — создаёт задачу и активирует её; краткосрочная память
  очищается.
- `/task switch <name>` — активирует существующую задачу; краткосрочная память
  очищается.
- `/memory clear short` — очищает краткосрочную память.
- `/memory clear working` — очищает записи текущей (активной) задачи.
- `/memory clear long` — очищает долговременную память.
- Одна активная задача на агента; задачи привязаны к агенту (файлы лежат в
  `memory/<agent>/`).

## Поведение при отсутствии активного профиля

Если файл `active_profile.txt` отсутствует или пуст — активного профиля нет.
В этом случае слой profile просто не подмешивается в промт, и агент работает
без него. Остальные слои продолжают работать как обычно.

## Поведение при отключённых слоях

- Каждый слой включается/выключается независимо командой
  `/memory usage <layer> on|off`; по умолчанию включены все пять
  (invariant, profile, long, working, short).
- Если слой `invariant` выключен — блок инвариантов не подмешивается в промт и
  пост-проверка не выполняется (даже если `/invariant check on`); файл
  `invariants.json` при этом не удаляется.
- Если все слои выключены — в LLM отправляется только system prompt + текущий
  запрос.
- Если активной задачи нет — рабочая память не используется и не сохраняется.

## Состояние задачи (FSM)

Задача может иметь **конечный автомат этапов** (state machine). Это опциональная
надстройка над рабочей памятью: если этапов нет, задача работает как обычный
диалог с рабочей памятью.

### Назначение

Автомат задаёт **этапы задачи** и **переходы** между ними. «Этап задачи»,
«текущий шаг» и «ожидаемое действие» — это одно и то же (один уровень); внутри
одного этапа отдельного «шага» нет.

### Структура этапа

Каждый этап описывается полями:

- `name` — короткое имя (используется в командах);
- `description` — что должно происходить на этапе (текст);
- `expected_action` — что ожидается от пользователя/агента на этом этапе (текст);
- `status` — `pending | active | completed`;
- `order` — порядковый номер.

У этапа **нет** поля `condition` — условие завершения переехало на переход.

### Структура перехода

Переход описывается полями:

- `id` — UUID;
- `from` — имя этапа-источника;
- `to` — имя целевого этапа;
- `condition` — условие перехода на естественном языке (оценивает LLM).
  Пустая строка означает, что переход не участвует в авто-проверке.

### Хранение

Состояние автомата — часть файла `working_<task_name>.json` в поле `fsm`:

```json
"fsm": {
  "stages": [ { "name": "...", "description": "...",
                "expected_action": "...", "status": "...", "order": 0 } ],
  "transitions": [ { "id": "uuid", "from": "...", "to": "...", "condition": "..." } ],
  "current_stage": "...",
  "paused": false,
  "completed": false
}
```

Если поле `fsm` отсутствует или равно `null` (старые задачи или задачи, где
`/task stages set` не вызывалась) — задача работает как раньше.

### Правила переходов

Переход между этапами возможен только если в `transitions` есть соответствующий
переход `from → to`. «Перепрыгнуть» этап нельзя.

- **Линейно по умолчанию.** Если пользователь не задал явный граф переходов, при
  `/task stages set` переходы генерируются линейно по порядку этапов:
  `stage[0] → stage[1] → ...`. Условия этих переходов — пустые строки.
- **Явный граф (опционально).** Пользователь может задать произвольный набор
  переходов (`/task transitions set`). Тогда линейная цепочка полностью
  заменяется.

Переход между этапами выполняется:

1. **Автоматически** — с подтверждением пользователя (см. ниже).
2. **Вручную** — командами:
   - `/task next` — перейти по разрешённому переходу вперёд (если их несколько —
     спросить, по какому);
   - `/task back` — вернуться назад (только при явном переходе current → previous);
   - `/task goto <name>` — перейти к этапу (только по разрешённому переходу).

При переходе текущий этап помечается `completed` (при движении вперёд) или
`pending` (при движении назад), целевой становится `active`.

### Автоматическая проверка условий

После каждого ответа агента автоматически проверяются условия всех исходящих
переходов текущего этапа. Проверка выполняется в рамках того же диалога: агент
в отдельном вызове LLM по каждому переходу задаёт вопрос с промтом вида:

```
Вот условие перехода: <condition>. Вот последний обмен: <user message> / <assistant response>. Ответь строго "да" или "нет".
```

- Если ни одно условие не выполнено — ничего не происходит.
- Если выполнено ровно одно — CLI сразу спрашивает пользователя:
  «Условие перехода <from> → <to> выполнено. Перейти? [y/n]».
- Если выполнено несколько — выводится список сработавших переходов и
  спрашивается, по какому перейти.
- Если пользователь ответил «нет» — при следующем сообщении пользователя
  проверка выполняется снова.
- Переходы с пустым условием (`condition == ""`) не участвуют в авто-проверке;
  по ним можно перейти только вручную (`/task next` / `/task goto`).

Ту же логику можно запустить вручную командой `/task check`.

### Терминальное состояние

Если у текущего этапа нет исходящих переходов — задача помечается завершённой
(`fsm.completed = true`), рабочая память задачи (записи `records`) очищается,
файл сохраняется. Это же происходит, если после подтверждённого перехода
целевой этап в свою очередь не имеет исходящих переходов.

### Недопустимые переходы

При попытке выполнить недопустимый переход (`/task next` без разрешённых,
`/task back` без явного обратного перехода, `/task goto` без перехода) следует
отказ с сообщением:

```
Переход <current> → <target> не разрешён. Допустимые переходы из <current>: <список или "нет">.
```

Переход на несуществующий этап также отклоняется (сообщение «Этап «<name>» не
найден. Допустимые переходы из <current>: ...»). В любом случае недопустимый
переход не изменяет состояние задачи и не помечает её завершённой.

Обходных путей (`--force`) не предусмотрено.

### Обратная совместимость

Старые задачи из Task 13/14 (поле `condition` внутри этапа, без `transitions`)
при загрузке автоматически конвертируются в новую схему: `transitions`
генерируются линейно, `condition` каждого этапа переезжает в переход
`stage[i] → stage[i+1]`; из этапов поле `condition` удаляется. Конвертация
выполняется при первом чтении файла и сохраняется обратно.

### Пауза и завершение

- `/task pause` — `fsm.paused = true`: автомат не двигается, автоматические
  проверки не запускаются, блок состояния не подмешивается в промт.
- `/task resume` — снять с паузы.
- `/task restart` — начать задачу заново с первого этапа: первый этап становится
  `active`, остальные — `pending`, `paused = false`, `completed = false`;
  этапы и переходы сохраняются, а краткосрочная память очищается.
- Завершённая задача (`fsm.completed = true`) — блок состояния не подмешивается;
  рабочая память очищена.

### Порядок блока состояния в промте

Если у активной задачи есть этапы и задача не на паузе и не завершена, в промт
добавляется блок:

```
[СОСТОЯНИЕ ЗАДАЧИ]
Текущий этап: <name>
Описание этапа: <description>
Ожидаемое действие: <expected_action>
Допустимые переходы:
  → <to>  (условие: <condition>)
  → <to2> (условие: <condition2>)

Работай в рамках текущего этапа. Не переходи к следующему, пока не выполнено условие соответствующего перехода.
```

Если переходов нет — блок подмешивается с пометкой, что задача завершается.

Порядок в общем промте: `system prompt → invariants → profile → long-term →
working → блок состояния → short-term → текущий запрос`.
