# Week1Task14 — агент с явной многослойной моделью памяти, инвариантами и конечным автоматом задач

Локальное Python-приложение: библиотека агента и CLI-интерфейс. Агент —
отдельная объектная сущность, инкапсулирующая работу с LLM и независимыми
слоями памяти.

Слои памяти:

- **invariants** — жёсткие ограничения, которые агент не имеет права нарушать
  (`memory/<agent>/invariants.json`); высший приоритет;
- **profile** — предпочтения пользователя по стилю, формату, ограничениям
  (`memory/<agent>/profiles/<name>.json`, активный — в
  `memory/<agent>/active_profile.txt`);
- **short-term** — лог диалога в рамках активной задачи (`memory/<agent>/short_term.json`);
- **working** — данные текущей задачи (`memory/<agent>/working_<task_name>.json`);
- **long-term** — решения и знания (`memory/<agent>/long_term.json`).

Подробное описание модели памяти — в [MEMORY_MODEL.md](MEMORY_MODEL.md).

## Установка

Требуется Python 3.10+.

```bash
python -m pip install -r requirements.txt
```

Зависимости: `httpx`, `rich` (rich опционален — CLI работает и без него).

## Конфигурация

Файл `config.json` в корне проекта описывает провайдеров и агентов (см. пример в
репозитории). Приоритет источников значений: **CLI-аргументы → env → config.json**.

```jsonc
{
  "default_agent": "assistant",
  "providers": {
    "deepseek": { "type": "openai_compatible" }
  },
  "agents": {
    "assistant": {
      "provider": "deepseek",
      "model": "deepseek-chat",
      "endpoint": "https://api.deepseek.com",
      "api_key_env": "DEEPSEEK_API_KEY",
      "system_prompt": "...",
      "temperature": 0.7,
      "max_tokens": 1024,
      "top_p": 1.0,
      "top_k": 50,
      "memory_dir": "memory/assistant"
    }
  }
}
```

## Переменные окружения

- `DEEPSEEK_API_KEY` — API-ключ (имя задаётся полем `api_key_env` в конфиге).
  Ключ **никогда** не хранится в `config.json`.
- `DEFAULT_AGENT` — переопределяет `default_agent` из конфига (env > config).

## Запуск CLI

Интерактивный режим:

```bash
python cli.py
python cli.py --agent coder
python cli.py --config path/to/config.json
```

Одноразовый режим (один запрос — один ответ):

```bash
python cli.py --prompt "Привет!"
```

В интерактивном режиме строки, начинающиеся с `/`, обрабатываются как команды,
остальные — как сообщения агенту.

## Профили

Профиль — отдельный слой памяти, более приоритетный, чем long-term. Он описывает
пользователя: предпочтения по стилю, формату, ограничениям. У каждого агента —
свой набор профилей; активный профиль хранится в файле
`memory/<agent>/active_profile.txt`.

| Команда | Описание |
| --- | --- |
| `/profile list` | список профилей агента (активный помечен) |
| `/profile current` | показать имя активного профиля |
| `/profile show [<name>]` | показать содержимое профиля (по умолчанию — активного) |
| `/profile new <name>` | создать профиль с пустыми обязательными полями |
| `/profile switch <name>` | сделать профиль активным (обновляет `active_profile.txt`) |
| `/profile del <name>` | удалить профиль (если он был активным — активный становится не задан) |
| `/profile set <name> style\|format\|constraints <value>` | задать поле профиля |
| `/profile unset <name> style\|format\|constraints` | очистить поле профиля (пустая строка) |
| `/profile add-note <name> <текст>` | добавить заметку в `notes` |
| `/profile del-note <name> <index>` | удалить заметку по индексу |

Если активного профиля нет — слой просто не подмешивается в промт. Включить или
выключить слой в промте можно командой `/memory usage profile on|off`
(по умолчанию — on).

## Инварианты

Инварианты — жёсткие ограничения, которые агент не имеет права нарушать:
выбранная архитектура, принятые технические решения, ограничения по стеку,
бизнес-правила. Это отдельный слой, **более приоритетный, чем профиль**.

- Хранятся отдельно от диалога: один файл на агента —
  `memory/<agent>/invariants.json`.
- Привязка — к агенту (не к задаче, не глобально). Действуют всегда: и при
  активной задаче, и без неё, и при задаче на паузе, и при завершённой задаче.
- Структура записи: `id` (UUID), `category` (`architecture | tech | stack |
  business | other`), `text`, `ts` (ISO 8601).
- Соблюдение — гибридно: блок инвариантов подмешивается в промт, а опционально
  ответ агента дополнительно проверяется **LLM-валидатором** (пост-проверка).
- Если валидатор вернул `VIOLATION` — пользователю показывается только текст
  отказа «Предложенное решение нарушает инвариант X.», исходный ответ агента не
  показывается.

| Команда | Описание |
| --- | --- |
| `/invariant list` | список инвариантов агента (ID, категория, текст) |
| `/invariant add <category> <текст>` | добавить инвариант |
| `/invariant del <id>` | удалить инвариант по ID |
| `/invariant edit <id> <текст>` | изменить текст инварианта |
| `/invariant clear` | очистить все инварианты |
| `/invariant check on\|off` | вкл/выкл пост-проверку LLM-валидатором (по умолчанию off) |

Слой инвариантов включается/выключается в промте командой
`/memory usage invariant on|off` (по умолчанию on). Если слой выключен — блок
инвариантов не подмешивается и пост-проверка не выполняется (даже при
`/invariant check on`); файл `invariants.json` при этом не удаляется.

## Конечный автомат задачи (FSM)

Задаче можно задать **этапы** и **переходы** между ними (state machine). Пока
этапов нет — задача работает как обычный диалог с рабочей памятью. «Этап»,
«текущий шаг» и «ожидаемое действие» — одно и то же (один уровень).

Этап состоит из: `name` (короткое имя для команд), `description`,
`expected_action`, `status` (`pending | active | completed`), `order`.

Переход описывается полями: `id` (UUID), `from`, `to`, `condition` (условие на
естественном языке, оценивает LLM; пустая строка — переход не участвует в
авто-проверке).

| Команда | Описание |
| --- | --- |
| `/task stages list` | показать этапы и исходящие переходы (активный помечен) |
| `/task stages set` | полностью перезаписать набор этапов (интерактивно); очищает рабочую память, первый этап — active, генерируется линейный граф переходов |
| `/task transitions list` | показать все переходы задачи (from → to, условие) |
| `/task transitions set` | полностью перезаписать граф переходов (интерактивно) |
| `/task transitions add <from> <to> "<condition>"` | добавить переход |
| `/task transitions del <id>` | удалить переход по ID |
| `/task transitions edit <id> condition "<текст>"` | изменить условие перехода |
| `/task transitions clear` | очистить все переходы (задача станет терминальной) |
| `/task state` | показать состояние: этап, ожидаемое действие, допустимые переходы, статус, пауза/завершено |
| `/task next` | перейти по разрешённому переходу вперёд |
| `/task back` | вернуться назад (только при явном обратном переходе) |
| `/task goto <name>` | перейти к этапу (только по разрешённому переходу) |
| `/task check` | вручную проверить условия исходящих переходов |
| `/task pause` | поставить задачу на паузу (автомат не двигается, проверки и блок состояния отключены) |
| `/task resume` | снять с паузы |
| `/task restart` | начать задачу заново с первого этапа (краткосрочная память очищается) |

Если пользователь не задал явный граф переходов, задача выполняется **линейно**:
после `/task stages set` автоматически генерируются переходы
`stage[0] → stage[1] → ...` с пустыми условиями.

После каждого ответа агента автоматически проверяются условия всех исходящих
переходов текущего этапа через отдельный вызов LLM. Если сработал ровно один
переход — CLI спрашивает «Условие перехода <from> → <to> выполнено. Перейти?
[y/n]»; если несколько — выводит список и спрашивает, по какому перейти. Если у
текущего этапа нет исходящих переходов — задача помечается завершённой, а
рабочая память очищается.

### Пример задания этапов и переходов

```text
[assistant]> /task new mvp
[assistant]> /task stages set
Сколько этапов задать? 3
  Этап 1/3 — имя (короткое, для команд): planning
  Описание этапа: Составить план реализации
  Ожидаемое действие: Предложить план и получить подтверждение
  Этап 2/3 — имя (короткое, для команд): execution
  Описание этапа: Реализовать код по плану
  Ожидаемое действие: Написать работающий код
  Этап 3/3 — имя (короткое, для команд): validation
  Описание этапа: Проверить результат
  Ожидаемое действие: Показать результат и получить подтверждение
Набор этапов задан: planning, execution, validation. Рабочая память очищена, первый этап активен. Сгенерирован линейный граф переходов (условия пустые).

[assistant]> /task transitions list
Переходы задачи:
  <id>: planning → execution  (условие: —)
  <id>: execution → validation  (условие: —)

[assistant]> /task transitions edit <id> condition "План согласован с пользователем"
Условие перехода <id> обновлено: План согласован с пользователем.

[assistant]> /task state
Состояние задачи:
  Этап: planning
  Описание: Составить план реализации
  Ожидаемое действие: Предложить план и получить подтверждение
  Статус: active
  Пауза: нет
  Завершено: нет
Допустимые переходы из текущего этапа:
  → execution  (условие: План согласован с пользователем)
```
